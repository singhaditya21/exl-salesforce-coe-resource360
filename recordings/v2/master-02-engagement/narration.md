# Master 02 — Engagement 360: Account to Delivery

## Intro

Welcome to Master Recording 02 for EXL Salesforce COE Resource 360. This walkthrough covers the complete Engagement 360 module, from ENG-01 through ENG-08, using the authenticated Salesforce application and fictional demonstration data. The operating chain is straightforward: an account can sponsor multiple projects; each project is represented as an engagement and can carry multiple commercial references, budgets, resources, timesheets, work units, risks and allocation versions. In this recording we will inspect that chain through the portfolio list, commercial overview, current roster, budget economics, delivery actuals, work plan, accountable risk register and allocation history. The current demo baseline contains ten accounts and twenty rich engagement records, with sixty active resources and the related records needed to show project governance. Every screen is server scoped by role, portfolio, confidentiality, effective dates and source freshness. Salesforce is the transactional system of record. GitHub Pages is only the synchronized, read-only showcase. The name visible in the authenticated header has been replaced with Demo User; no credential, production identity, browser chrome or unrelated tab is recorded.

## ENG-01 — Engagement list

We begin at ENG-01, the scoped engagement portfolio. The module rail on the left confirms that this is the first of eight Engagement 360 screens, and the summary cards retain enterprise capacity and commercial context while we navigate. The workbench is returning twenty engagement records through Salesforce user-mode scope. The seeded portfolio spans industries such as automotive, banking, healthcare, insurance, consumer goods, education, energy, retail, high technology, hospitality, life sciences, transportation, manufacturing, media, government, telecommunications, travel and utilities. Each row carries the engagement name, project identifier and owner context, delivery state, Salesforce cloud or solution tower, industry and effective date. Active and completed records appear together so portfolio and account leaders can separate current delivery from historical work without losing lineage. Global Retail Cloud, for example, is an active Data Cloud retail engagement, while completed projects remain discoverable for audit and reference. The governed contract authorizes Project Managers, COE Staffers, Portfolio Managers, Account Owners, Finance, Operations, Auditors and executive roles, but the visible row set is still determined on the server. The primary action is a new engagement view, and route, record drill-down and engagement-open events remain traceable.

## ENG-02 — Engagement 360 overview

ENG-02 brings commercial and delivery context together. The workbench shows forty-one commercial references related to the twenty engagements, demonstrating that one project can carry more than one SOW, purchase order, amendment or change order. That one-to-many relationship is essential: commercial authorization can evolve without overwriting the original contract. The newest rows make the lineage tangible. Global Retail Cloud retains an eight point four crore SOW, a sixty-lakh amendment and a ninety-lakh change order as separate governed references. Consumer Loyalty Transformation carries its own six point nine crore SOW, and the wider seeded portfolio includes active and expired reference states. The screen reconciles engagement, SOW or PO context, state, evidence value and source cutoff before downstream staffing or budgeting actions are allowed. This is not a browser-side join. The server contract uses scoped engagement selectors and user-mode SOQL, with portfolio, confidentiality, freshness and effective-date checks applied before records reach the component. The primary route from this overview is Open Staffing, linking commercial authority to the resource demand it funds. For an Account Owner or Project Manager, this screen is the 360-degree answer to what was sold, which project it supports, whether it is current and what evidence authorizes delivery.

## ENG-03 — Resources tab

On ENG-03 we move from commercial intent to the current engagement roster. Salesforce returns one hundred thirty-eight accepted allocation records across sixty active resources. Each row preserves the practitioner, engagement, delivery role, commercial classification, daily hours, allocation version, acceptance state and effective date. That means the same person can be assigned to more than one project and every project can have multiple resources, while each assignment remains independently governed. The seeded data includes Salesforce developers, Service Cloud leads, Data Cloud architects, MuleSoft architects and developers, program managers, quality engineers, integration developers, Experience Cloud leads, analytics specialists and AI consultants. Classification distinguishes Billing from WAR, IFB or PO Awaited, Training and other operating states. The current capacity policy is visible in the module KPIs: all sixty active resources reach at least eight aggregate hours, fifty are exactly balanced, and ten are deliberately overallocated under controlled exception. A single allocation line cannot exceed eight hours, but valid split assignments can sum across projects; approved over-allocation is permitted up to twelve hours with warning, reason, approver and audit. ENG-03 therefore shows staffing truth, not a flat contact list. The Add Resource action begins governed placement, while later staffing masters will demonstrate matching by industry, functional and technical skill.

## ENG-04 — Budget tab

ENG-04 exposes current budget economics for every project. Twenty budget records are visible, and only the signed current version is allowed to drive staffing and profitability controls. The table carries the budget number, engagement and version, approval state, approved revenue, calculated gross margin, approval evidence and as-of date. Global Retail Cloud is on version four with eight point four crore approved revenue and a thirty-two point three eight percent margin; it has been auto-approved because it clears the configured thirty-percent threshold. Consumer Loyalty Transformation is on version three with six point nine crore revenue and a twenty-six point two seven percent margin, so it remains Pending Approval and is routed to the Portfolio Manager. Other seeded projects carry approved governed economics for cross-industry comparison. This screen makes three rules explicit. First, revisions create versions instead of silently changing the signed baseline. Second, the approval state is evidence, not decoration: a pending or rejected version cannot become the staffing authority. Third, revenue and margin are calculated from the governed commercial and cost model, giving Project Managers, Budget Approvers, Finance and Portfolio Managers a shared financial truth. One budget is actionable now in this view, and Open Budget moves directly into the approval and work-breakdown workflow covered in a later master.

## ENG-05 — Actuals and timesheet tab

ENG-05 connects the delivery plan to submitted and approved actual effort. Twenty-five timesheet records are currently visible, with two items requiring action. Every row retains the resource, week, workflow state, exception or approval evidence and accountability date. The examples include submitted weeks ready for review, approved weeks that passed allocation and daily-capacity checks, and a correction-pending record routed to the Timesheet Approver. This separation matters because an allocation is permission and intent, while a timesheet is actual work performed. Resource 360 allows controlled planned over-allocation, but actual timesheet entry remains capped at eight hours per day unless a separately governed overtime policy is enabled. Approval therefore reconciles the submitted hours with the effective allocation, project, work unit, calendar and capacity ledger. Exceptions are named and attributable rather than buried in a total. Project Managers use the view to understand delivery consumption; People Managers and Timesheet Approvers use it to act; Finance and PMO use approved actuals for margin and utilization reporting; practitioners see only their authorized records. The Export Actuals action preserves a controlled downstream evidence path. Later timesheet masters will show preparation, submission, correction, approval, reminders, reconciliation and the audit history in detail.

## ENG-06 — Work plan and milestones

ENG-06 is the work plan and milestone view. It contains one hundred twenty-two work-unit records across the portfolio, showing how a project is decomposed into manageable delivery scope rather than tracked as one undifferentiated engagement. Each row carries the work-unit or milestone name, parent engagement, delivery phase, current state, WBS code and date. In Global Retail Cloud, Discovery and retail journeys and Data Cloud architecture are complete; Service Cloud build and the MuleSoft integration factory are active; and a cancelled Data Cloud Foundation item remains visible instead of being erased. This hierarchy supports project modules, work units, milestones and the budgets and timesheets that refer to them. The WBS code is the common key that aligns scope, cost and actual effort. Phase values such as Discover, Design and Build allow the Gantt and dashboards to roll individual activities into a project trajectory. Status history distinguishes planned, active, complete, cancelled and blocked work, while owner context and dates establish accountability. The primary Add Milestone action is role governed. Project Managers can maintain the delivery plan, while Portfolio, Finance, Operations and audit personas receive the appropriate read or exception view. This becomes the backbone for schedule publication, completion tracking and earned-value analysis.

## ENG-07 — Risks and actions

ENG-07 makes operational exceptions accountable. The risk and action register shows ten current records, nine of them open and actionable. Rather than presenting a generic warning badge, every item retains the original trigger, severity, assigned owner, first-seen time, current state and eventual closure evidence. The visible examples cover a critical integration exception caused by fictional People Master validation failures, a high-priority budget decision assigned to the Executive Approver, a staffing decision inside its twelve-hour service level, a timesheet approval due for the People Manager and an expired staffing request routed back to the Project Manager. These records bridge project delivery with the cross-functional work required to resolve it. Severity supports triage, the owner establishes who must act, and the timestamp prevents the service-level clock from resetting when an item changes hands. Closed items remain available for audit and recurring-pattern analysis. The Add Action route lets an authorized role create a managed response, but scope and confidentiality are still enforced by Salesforce before write authority is granted. For a Project Manager this is the daily control list; for Operations it is the exception queue; for executives it is an aggregated risk posture; and for auditors it is attributable evidence from trigger to closure.

## ENG-08 — Allocation history

The final Engagement 360 screen, ENG-08, preserves effective-dated allocation history. One hundred thirty-eight allocation rows are available in the current seeded baseline. The table repeats the familiar practitioner, engagement, role, commercial classification, daily hours, version, acceptance state and date because those fields form the staffing lineage. What changes over time is never collapsed into an unexplained current percentage. The originating staffing request, allocation version, state transition and effective window can be followed from proposal to acceptance, amendment, expiry or release. This is particularly important for split assignments and controlled over-allocation. A practitioner might carry separate project lines that together equal the standard eight-hour day, or exceed it under an approved exception; each line keeps its own project, hours and dates while the central capacity ledger evaluates the aggregate. The history also supports billing classification changes, project closeout, utilization reconciliation and proof that an old allocation no longer authorized time entry. Export History provides governed evidence without making the browser the source of truth. Project Managers see the lineage for their engagements, Staffers see placement history, People Managers see resource impact, Finance and PMO reconcile the commercial classification, and Auditors can reconstruct who was assigned where, for how long and under which decision.
